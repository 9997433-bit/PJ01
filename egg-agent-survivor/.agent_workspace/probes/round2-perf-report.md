# Round 2 性能优化报告

## 环境与口径

- 时间：2026-08-26（UTC）
- 系统：Linux 6.12.94+，Google Chrome 148.0.7778.96，无头模式
- 浏览器渲染：SwiftShader；窗口 1280×800，游戏 Canvas 1280×713，DPR 1
- 独立探针：`tests/benchmark.html`，Canvas 1265×633
- 采样：预热 1.5–2.5 秒，采样 5–6 秒
- R1 的 36 FPS 是任务给定结果；因原始注入脚本和设备参数缺失，不与本轮受控数据混算。

## 结果

| 场景 | 版本 | 平均 FPS | 1% Low | P95 帧耗时 | >50ms 长帧 |
| --- | --- | ---: | ---: | ---: | ---: |
| 500 敌人简化探针 | 优化前 | 60.0 | 59.5 | 16.7ms | 0 / 301 |
| 500 敌人 + 3000 批量粒子压测 | 优化后 | 60.0 | 59.5 | 16.8ms | 0 / 301 |
| 500 敌人 + 满级六武器 + Boss + 长寿命粒子 | 优化前 | 16.0 | 10.0 | 83.4ms | 53 / 97 |
| 同上，启用自适应降级 | 优化后 | 46.5 | 15.0 | 50.0ms | 10 / 280 |

完整游戏受控场景中，平均 FPS 提升约 190%，P95 帧耗时下降约 40%，
长帧占比由 54.6% 降到 3.6%。优化后自动进入 `performance` 档：

- 500 个目标最终分为 184 个完整渲染、165 个 LOD1、150 个 LOD2；
- 粒子池容量为 3000，采样末 1073 个活跃粒子中绘制 412 个；
- 412 个粒子合并为 6 个 Canvas 批次；
- 低档位按 2 帧步长绘制，逻辑更新仍跟随每次 RAF。

## 实现

1. `GameEngine.js`
   - 120 帧无分配滚动 FPS 窗口；
   - `high / balanced / performance` 三档迟滞切换；
   - 降低粒子发射与绘制比例，严重负载时跳帧渲染；
   - 性能档关闭实体 Y 排序，并提供 `getPerformanceSnapshot()`。
2. `Enemy.js`
   - 敌人自身执行矩形视锥剔除；
   - 依据相机距离和质量档位选择完整、LOD1、LOD2 绘制；
   - Boss 始终保留完整读招，远处普通敌人移除阴影、眼睛与状态细节。
3. `ParticleSystem.js`
   - 默认池由 1400 扩到 3000；
   - 空闲栈与紧凑活跃索引使获取、释放为 O(1)；
   - 按形状、颜色、透明度和线宽批量提交 Canvas 路径；
   - 性能档固定哈希抽样，减少绘制且不产生逐帧闪烁。
4. `benchmark.html`
   - 新增“500 敌人压测”和 `?stress=1`；
   - 压测叠加 3000 个批量粒子；
   - 新增 FPS 历史图、60/30 FPS 参考线和可机读结果。

## 复现

`window.__benchmarkResults`。

## 验证与结论

- `npm run probe`：9/9 通过；
- 改动的 JavaScript 均通过 `node --check`；
- 500 + 3000 独立压测无浏览器异常；
- Node 全套测试首次运行有一个依赖随机战斗结果的既有用例波动，单独重跑
  `tests/boot.test.js` 为 6/6 通过。

独立 500 敌人压测已达到 60 FPS。完整满武器/Boss 场景在当前无头
SwiftShader 环境达到 46.5 FPS，尚未达到 60 FPS，因此不能把独立探针的
60 FPS 结论外推到完整游戏。后续若完整场景也必须稳定 60 FPS，应继续拆分
武器特效、碰撞查询和 Canvas 合成开销，并在目标 GPU 真机上校准降级阈值。
